The quiet beauty of small software.

Santosh K.
Founder & writer · Nebula
✦

Somewhere between the rise of the App Store and the arrival of cloud-everything, we forgot that software could be small. Not minimal, exactly — minimal is an aesthetic. Small is a posture: a refusal to expand beyond what a thing needs to be, a preference for the local over the remote, the legible over the clever.

The first piece of software I ever loved was a text editor that fit on a floppy disk. It had no plugin system. It did not sync. It opened in the time it took me to look up at the screen. When I close my laptop tonight and reach for whatever has replaced it, I will be opening four electron windows, each of which loads a JavaScript runtime to display a list of files.

The best software I use now is the software that respects my attention enough to disappear when I am done with it.

What "small" actually means

Small software is not about line count. A compiler can be small. A database can be small. sqlite is small in this sense; it is also somehow the most-deployed database in the world. Smallness is about fit: how closely a piece of software hugs the contours of the problem it is solving, with no slack for hypothetical futures.

The signs of small software, as I have come to recognize them:

  • It boots instantly. Cold start is a feature, not a metric.
  • It does one job, and the job is the noun in the product's name.
  • It writes its data to a file you could open with another tool.
  • It runs offline by default and treats the network as a bonus.
  • Its settings page fits on one screen.

A simple example

I keep a script in ~/bin called jot. It is forty-three lines of shell. It appends a timestamped paragraph to a single text file. I have used it almost every day for five years. It has no backend, no auth, no settings, no website, and no plans. I do not pay anyone for it. I will not lose access to it when a startup pivots. 

#!/bin/sh
echo "## $(date '+%Y-%m-%d %H:%M')" >> ~/journal.md
${EDITOR:-vim} ~/journal.md

The first time I showed someone this, they asked when I was going to "build it out." I think the answer is "never." It is finished. There is nothing here to build out.

The economics of restraint

The standard model of software economics rewards growth: more users, more features, more surface area to defend with more engineers. This is a fine model for some categories. It is a deeply strange fit for the categories we apply it to most aggressively — note-takers, to-do lists, calendars, writing tools. The things, in other words, that we use to think.

When a tool for thinking grows, it grows away from the user. It accumulates other people's workflows. It adds opinions about how a meeting should be structured, or what a "project" is. Every new feature is a small tax on the original idea.

A counter-economics

The interesting work happening on the edges of the web right now is, I think, an experiment in a different economics: tools sold once, code that lives on a single developer's GitHub for a decade, and local-first projects that treat sync as a sometimes-feature instead of an architecture.

None of this is new. It just feels new because we spent fifteen years pretending it wasn't a choice.

What I am trying to do

I am trying, mostly, to ship less. To finish more. To resist the gravitational pull of and also. When I sit down to start something new, I try to write the smallest version of the README first — not the smallest version that would impress anyone, but the smallest version that would be useful to me on a Tuesday.

The funny thing is that the result usually looks, to an outsider, like restraint. From the inside, it just feels like clarity.
